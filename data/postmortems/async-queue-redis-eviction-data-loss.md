# Async queue redis eviction data loss

## Date
2026-10-15

## Authors
Incident Response Team

## Status
Final

## Summary
On October 15th, 2026, memory pressure on the `redis` cluster caused it to aggressively evict data to stay under its limits. Because the async job queue used for processing API usage events was stored in this same `redis` cluster, thousands of pending usage events were silently evicted, leading to permanent data loss and underbilling.

## Impact
SEV1. Approximately 45,000 API usage events were lost. This resulted in an estimated $8,500 of unbilled API usage for our highest-tier customers. 

## Root Cause
The `api_gateway` pushes raw API usage events onto an async job queue backed by `redis`, which are later consumed by the `billing_service`. The `redis` cluster is also used heavily by the `auth_service` for caching. A sudden spike in user logins caused a massive influx of cached session data, pushing `redis` memory utilization to 100%. The cluster was configured with an `allkeys-lru` eviction policy. To make room for new cache keys, `redis` began silently deleting the oldest keys, which included the lists backing the async job queue. The `billing_service` never received these evicted events, resulting in permanent data loss.

## Trigger
A marketing push resulted in a sudden 300% spike in user logins, overflowing the `redis` cache capacity.

## Resolution
The eviction policy on the `redis` cluster was immediately changed to `volatile-lru` to prevent eviction of keys without a TTL (like our job queues). We unfortunately had to accept the loss of the 45,000 events as they were not backed up elsewhere.

## Detection
The data engineering team noticed a severe drop in processed events in the `postgres` data warehouse compared to the raw request logs generated by the `api_gateway`.

## Timeline
- 2026-10-15T18:00:00Z - Marketing campaign launches; login traffic spikes.
- 2026-10-15T18:15:00Z - `redis` memory hits 100% capacity.
- 2026-10-15T18:16:00Z - `redis` begins evicting job queue lists via `allkeys-lru`.
- 2026-10-15T19:00:00Z - Login spike subsides; memory pressure eases.
- 2026-10-16T09:00:00Z - Data team detects massive discrepancy in daily usage counts.
- 2026-10-16T11:00:00Z - Engineering identifies Redis eviction policy as the culprit.

## Action Items
- Separate critical queues from ephemeral caches by migrating the async job queue to a dedicated, persistent message broker (e.g., RabbitMQ or Kafka).
- Change the `redis` eviction policy to `volatile-lru` on all shared clusters.
- Add alerts for `redis` eviction events.

## Lessons Learned
Mixing persistent data (queues) and ephemeral data (caches) in the same datastore with aggressive eviction policies guarantees data loss under load. Queues require durable storage mechanisms.
